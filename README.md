# Puddle

A browser-based data cleansing and preparation tool in the spirit of Power Query, built on DuckDB running inside the browser. Load messy files, wire a flow of cleaning steps on a node canvas, check the result against quality rules and export tidy data.

Nothing leaves your browser. Projects save the steps, not the data.

## Development

Needs Node 20 or later.

```sh
npm install
npm run dev        # http://localhost:5173
npm run lint
npm run typecheck
npm test           # unit tests, plus engine tests on real DuckDB-WASM (Node build)
npm run e2e        # Playwright against a production build (run `npx playwright install chromium` once)
npm run fetch-extensions  # optional: serve DuckDB's json and parquet extensions locally
npm run docs              # the user guide, with Sphinx (pip install -r docs/requirements.txt first)
npm run docs:screenshots  # retake the user guide's screenshots
```

Google Drive sync needs a Google Cloud OAuth client ID (type "Web application") in `VITE_GOOGLE_CLIENT_ID` at build time, e.g. `VITE_GOOGLE_CLIENT_ID=1234-abc.apps.googleusercontent.com npm run build`, or `--build-arg VITE_GOOGLE_CLIENT_ID=...` for the Docker image. Without it every Google Drive option is hidden. Add the site's origin (and `http://localhost:5173` for development) as an authorised JavaScript origin, and the same origin followed by `/` as an authorised redirect URI, and enable the Google Drive API for the project. Puddle asks only for the `drive.file` scope. The e2e build uses a test-only ID against a mocked Google.

SheetJS, which reads Excel workbooks, is vendored as `vendor/xlsx-0.20.3.tgz`: its current releases are published on cdn.sheetjs.com, not the npm registry (where `xlsx` stopped at 0.18.5, which has known vulnerabilities). `npm ci` installs it from that file, so installs need no access to the CDN. To upgrade, replace the tarball with a newer one from cdn.sheetjs.com and run `npm install --save-exact xlsx@file:vendor/<tarball>`.

## Tests

Every feature ships with its own tests, and every bug fix with a regression test, so later changes can't silently break earlier work. Logic lives in unit and engine tests; each user-facing flow has one Playwright test that shows it working in a real browser. `npm test` runs the pure and engine tests with one shared module registry per worker (`--no-isolate`, about twice as fast), then the component tests and the few files that mock modules in isolation; `vite.config.ts` lists which is which. CI (`.github/workflows/ci.yml`) runs lint, typecheck, the unit and engine tests, and the Playwright suite in Chromium and Firefox on every pull request, each browser split into shards that run as parallel jobs. WebKit (Safari's engine) runs the suite against main every night at 03:00 UTC (`.github/workflows/nightly.yml`), and on demand from the Actions page ("Run workflow"); a red nightly run emails the repository owner. CI also retakes the user guide's screenshots and builds the guide with Sphinx, warnings as errors, and builds the Docker image for amd64 and arm64 and runs `npm run e2e:container` against it: isolation headers, JSON and Parquet from the self-hosted extensions, and offline use.

## Deploying

A Docker image (nginx serving the static build) behind a Cloudflare Tunnel at puddle.kevspowertools.com. `docker compose up -d` runs it on <http://localhost:8088>, and `docker compose --profile tunnel up -d` adds the tunnel. See [deploy/README.md](deploy/README.md).

## Layout

| Path | What lives there |
|---|---|
| `src/design-system/` | Tokens, Tailwind preset and component CSS, vendored from the Puddle design system |
| `src/ui/` | The design system's components in TypeScript (`Button`, `NodeCard`, `StepList`, `RuleRow` and the rest), and how numbers and dates are shown: the display locale (`locale.ts`, per device) and the one formatting module (`format.ts`) |
| `src/app/` | The app shell: the seven-control toolbar (project menu, Add, undo, redo, Help, inspector toggle), inspector and results docks, status strip, theme, engine boot, per-tab session state |
| `src/engine/` | DuckDB-WASM in a Web Worker and the typed `EngineClient` (priorities, cancellation, Stop, plain-word errors) |
| `src/model/` | The project graph: Zod schemas, wiring rules, step edits, grouping, undo and redo |
| `src/compiler/` | The pure graph-to-SQL compiler (steps, joins and lookups over two inputs, appends over any number, queries from the query designer, hand-written SQL nodes over any number of inputs, Schema table nodes and the checks on what loads into them, and the scratch console), the DuckDB DDL of the project's DBML (`ddl/`), step registry, schema cache, the schema book those nodes read their inputs’ columns from, and how each locale writes numbers and dates for the parse steps (`locales.ts`). `ddl/` writes a DBML schema as DDL: `duckdb.ts` for the Schema tables built inside Puddle, and `script.ts` with one set of rules per database (`postgres.ts`, `mysql.ts`, `sqlserver.ts`, `sqlite.ts`, `duckdbScript.ts`) for **Export › SQL** on the Schema view |
| `src/sources/` | Adding sources: format detection from the bytes (`sniff.ts`: signatures, encodings, delimiter and header, with the Format picker when the content could be two things), file handles, clipboard text, web addresses (fetched again on reopen), tables on web pages (found and previewed in the From web page dialog, Wikipedia through its API, read as CSV; or a table copied from a page and pasted), OData feeds (`$metadata` read for the entity sets and their EDM types, every page read as JSON for versions 2 and 4, sign-ins kept in the tab only), choosing files again on reopen (on Chromium, reconnecting them with one permission click through stored file handles), Excel sources (sheet, header row and range, kept loaded as DuckDB tables), Access sources (a table each, kept loaded the same way, and the database's other tables added as sources sharing its file), and XML sources (record element and expanded element, read into CSV for DuckDB) |
| `src/xml/` | Reading XML without the DOM: a streaming reader (`parse.ts`), and turning repeating record elements into rows, with attributes and child elements as columns and repeats inside a record as JSON or a row each (`records.ts`). Pure, so the runner uses it too |
| `src/schema/` | Schema design from DBML (dbml.dbdiagram.io): the lexer, a parser that reports each mistake with its line and column and still reads the rest (`parse.ts`), the schema model and its Zod schema (`model.ts`: tables, columns, indexes, checks, refs, enums, groups, sticky notes, partials, records and diagram views, each with where it is in the text), the writer that turns the model back into DBML (`write.ts`), and edits made on the text in place by offset, so comments and formatting elsewhere stay (`edit.ts`: add a ref, rename a table or column with everything that names it, column settings, tables, colours, notes and groups). Pure, so the runner uses it too. The Schema view (`SchemaView.tsx`, project menu › Schema) pairs the DBML editor (`editor/`: highlighting, suggestions, bracket matching) with the live diagram (`diagram/`: geometry computed without the DOM and drawn as SVG; `place.ts` finds new tables a spot near their refs, `arrange.ts` auto-arranges with dagre, `palette.ts` maps DBML colours to the design tokens, `viewport.ts` pans and zooms, `editing.ts` and `DiagramEditing.tsx` edit the schema from the diagram: menus, renaming in place, a dragged ref), and diagram views (`views.ts` and the `SchemaViews.tsx` strip: named sets of tables with their own places, detail level and zoom, kept in the project as `schema.views`). **Export** on the Schema view: `diagram/exportImage.ts` makes the SVG on screen standalone (theme colours written onto each element) and draws PNG and a one-page PDF from it, `mermaid.ts` writes an erDiagram, and the SQL dialog uses `src/compiler/ddl/`. **Import SQL**: `sql/` reads PostgreSQL, MySQL and MariaDB, SQL Server, SQLite and DuckDB scripts into the schema model (statement splitting that understands strings, comments and `GO`, dialect detection, and a tolerant reader that warns per column), shown in `ImportSqlDialog.tsx`. **Sample data**: `sample/` generates rows that keep the design (types, keys, enums, checks the generator can read, refs with parents first, from a seed and a shipped word list) and writes them into the DBML as records (`FillSampleDialog.tsx`); a table's popover shows its data sample (`TableSampleView.tsx`, read by `src/schemaTables/sample.ts`). **Docs and sharing**: `docs.ts` writes one self-contained HTML page (tokens inlined, diagrams as SVG, contents and a search box) or Markdown (`ExportDocsDialog.tsx`); `share.ts` packs the DBML and layout into a link's `#schema=` fragment (deflate-raw, base64url), which `ShareDialog.tsx` offers with an embed snippet and `SharedSchema.tsx` opens read-only (or diagram-only with `&embed=1`) before the app starts. **Versions**: `versions.ts` keeps named copies of the DBML in `schema.versions`; `diff.ts` lists the changes between two schemas in words (renames detected) and diffs their lines, and `src/compiler/ddl/migration.ts` writes the migration script per dialect, shown in `VersionsDialog.tsx` |
| `src/schemaTables/` | Schema tables: the project's DBML built as real DuckDB tables (`build.ts`, in schemas named `dbml_<schema>`, with keys, foreign keys, checks, indexes and records; the runner builds them the same way), kept built while the editor is open (`state.ts`, rebuilt when the DBML changes), and **Add all tables** laid out as the diagram has them (`place.ts`). The DDL is generated in `src/compiler/ddl/duckdb.ts`; a Schema table node's rows, and the check that a load keeps every constraint, in `src/compiler/schemaTable.ts` |
| `src/access/` | Access databases (`.accdb`, `.mdb`) with mdb-reader in a Web Worker: listing the tables and reading one into typed columns and an Arrow table for DuckDB, each column given its Access type (Currency as an exact decimal) when it is loaded. The browser build leaves out the crypto mdb-reader needs only for password-encrypted databases (`noCrypto.ts`, aliased in `vite.config.ts`); `csv.ts` writes a table for the runner |
| `src/excel/` | SheetJS in a Web Worker: reading `.xlsx` sheets into typed columns and Arrow tables for DuckDB, and writing Excel exports from Arrow batches. Excel's limits and sheet-name rules live in `limits.ts`, which doesn't load SheetJS |
| `src/persistence/` | IndexedDB autosave, `.puddle.json` export and import, format migrations |
| `src/sync/` | Optional project sync through one provider-agnostic layer (`SyncProvider`): sync states, the offline queue, conflict choices and "Open from"; GitHub Gist and Google Drive (only with a client ID set at build time) are the providers. Credentials and sync links stay in IndexedDB on this device (Google's hour-long sign-in in this tab's session only); the synced file is the `.puddle.json` less pasted rows |
| `src/templates/` | Node templates: a Transform node's steps saved outside any project (IndexedDB, upgraded through the project migrations), the library dialog, and the column mapping that renames a template's columns for a new input and turns off steps whose columns are missing |
| `src/recipes/` | Recipes: a whole pipeline exported as `.puddle-recipe.json` with no data in it (no rows, file names, head hashes, kept results, pasted rows, header values or private parts of addresses), opened as a new project whose sources ask for files and take the column mapping from templates; templates as single-node recipes; the built-in gallery in `public/recipes` |
| `src/home/` | The projects home screen and the rename and delete dialogs |
| `src/samples/` | The onboarding samples: the catalogue of messy datasets in `public/samples/` (written by `scripts/make-samples.mjs`), the Try a sample picker, and `openSample`, which opens one as a new project |
| `src/tour/` | The guided tour: its stops, the popover that points at each part of the screen (following layout changes), the first-launch offer and progress kept in this browser |
| `src/canvas/` | The node canvas on React Flow: nodes, wires, auto layout |
| `src/flow/` | Each node's live status (columns, row count, broken, dimmed), kept in step with the project; sample mode above the row threshold |
| `src/steps/` | Each step type's editor form (`defineStepForm`): its Add step menu entry, fields and defaults; the expression editor |
| `src/dates/` | Date format detection: candidate `strptime` formats, ranking by match rate, day and month ambiguity |
| `src/quickfix/` | The quick-fix bar: one click on the selected columns adds one step where the viewed data is |
| `src/rules/` | Quality rule forms and labels; rules compile in `src/compiler/rules.ts` and are checked per node by `src/flow/rules.ts`. Rules derived from the schema (a node's **Check against the schema**, on by default when it loads a Schema table) are made in `src/model/schemaRules.ts`: rewritten from the DBML whenever it changes, marked `fromSchema`, kept as ordinary rules by **Add as rules** |
| `src/report/` | Quality reports: what the rules found (counts, overrides from the export log, sources with row counts and head hashes, opt-in failing rows) written as Markdown, JSON or one self-contained HTML file, and the export dialog |
| `src/pwa/` | The service worker (precached app, engine and extensions for offline use), its precache list and the web app manifest |
| `src/export/` | Exports from Output nodes: the quality gate, `COPY ... TO` into DuckDB's in-memory file system (Excel workbooks instead go through the Excel worker), download or clipboard, and the export log |
| `src/query/` | The query designer, in place of the canvas for a Query node: its tables and the join lines dragged between their fields, and the grid of fields with names, sorting, criteria (with "or" rows) and Show, and its Totals row for grouping and summarising |
| `src/relationships/` | The relationships view (project menu › Relationships), in place of the canvas: every source and Schema table as a table (a schema table's refs and keys included), lines between the columns the project's Joins, Lookups, Query join lines and "exists in" rules match (drawn on the table each column comes from), one or many at each end as DuckDB finds them, a dragged relationship kept as a rule, and the tables and relationships written as DBML, downloaded or opened in the Schema view |
| `src/inspector/` | The right-hand panel, in Node, Project and Notes tabs: source read options, applied steps, step settings, rules and node notes; project and display settings |
| `src/notes/` | The project notes (the inspector's Notes tab): Markdown written and previewed, rendered with raw HTML off and links in a new tab |
| `src/results/` | The results table on Glide Data Grid: paging, headers with type and quality |
| `src/runner/` | `puddle-run`: the same compiler on DuckDB’s native Node build, run from the command line or a container on your own machine: `run` a project file once, `watch` a folder and run each project on the cron schedule in its Project tab, `check` where its sources are, and `schema` checks a DBML or project file and writes its SQL, docs, Mermaid or migration for CI. Writes the outputs, a run log and a quality report; a failing `fail` rule holds an export back as the browser does. Built with `npm run build:runner`; see deploy/README.md |
| `src/console/` | The scratch SQL console under the results table: one query against the viewed node’s rows (read as `input`), answered in place without adding a node, and turned into a SQL node in one click |
| `tests/` | Engine integration tests, fixtures and helpers (`scripts/make-excel-fixtures.mjs` writes the Excel fixture and, under `tests/fixtures/formats/`, the same workbook in every other spreadsheet format, `scripts/MakeAccessFixtures.java` the Access ones, with Jackcess, `scripts/make-archive-fixtures.mjs` the gzip, zip and Arrow files under `tests/fixtures/archives/`, and `scripts/make-messy-fixtures.mjs` the four difficult files under `tests/fixtures/messy/` that the analyse-and-fix work is built against: an SAP list with a header and footer, a messy text export, a workbook whose rows skew, and a report with merged cells) |
| `e2e/` | Playwright tests |
| `docs/` | The user guide: Markdown pages built with Sphinx, and the Playwright script that takes its screenshots (`docs/screenshots/`) into `docs/_static/screenshots/` |

Adding a step type means one `defineStep` in `src/compiler/steps/` (Zod params, past-tense label, compile function), one `defineStepForm` in `src/steps/` (title, group, fields, defaults) and one test fixture. The form's column fields (`column`, `columns`, `renames`, `conditions`, `sortKeys`, `expression`, `sql`) are also how templates find and rename the columns a step reads.
